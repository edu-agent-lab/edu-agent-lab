`experiment/topic-retrieval`(팀원)과 `apps/ncic-rag`(내가 따로 만든 것)가 같은 일을
하고 있었다. 우연히 임베딩 모델(`dragonkue/BGE-m3-ko`)과 sparse 라이브러리(`rank_bm25`)
선택까지 같았다.

확정된 것 세 가지만 바꿨다. `apps/ncic-rag`는 삭제했다.

**최종: Top-1 8/10 · R@3 0.92 · R@10 0.97 · 노이즈 1 · 통과 33/38**

## 1. 상황 — 중복 작업이었다

| | `apps/ncic-rag` (내 것) | `apps/topic-retrieval` (팀원) |
|---|---|---|
| 인덱싱 범위 | 9,939건 (doc_type 4종) | 성취기준 5,789건 |
| 임베딩 입력 | 프리픽스+code+content+explanation | `content + area` |
| BM25 토크나이저 | 어절 + 문자 2-gram | kiwipiepy 형태소 |
| 결합 | 점수 정규화 + 가중합 | RRF (k=60) |
| 필터 | 부분 문자열(`in`), 점수에 `-inf` | 정확 일치(`==`), 리스트 축소 |
| 골든셋 | 22건 (must_not/0건/특수교육) | 19건 (course까지 좁힌 단일 정답) |
| 평가 | `--compare`, `--compare-filters` | stage별 비교 (골든셋은 미완료로 적혀 있었음) |

**원격 브랜치를 못 찾았던 이유**: `git fetch --all`로는 안 잡혔고
`git fetch origin "+refs/heads/*:refs/remotes/origin/*"`로 명시해야 받아졌다.

**README와 코드가 달랐다**: `build_index.py` 주석에 "원래 `text`로 임베딩했더니 5,789건에
4시간 걸려서 `search_text`(content+area)로 바꿨다"고 적혀 있는데 README는 `text` 기준으로
남아 있었다. 그래서 처음 비교에서 팀원 실제 조합을 테스트하지 못했고, 다시 측정했다.

## 2. 어느 구현이 나은가 — 양쪽 골든셋으로 교차 검증

16조합(dense 입력 2 × 토크나이저 2 × 결합 2 × BM25 대상 2)을 돌렸다.

**내 골든셋 22건에서는 내 조합이 1위**(14/22), **팀원 골든셋 19건에서는 kiwi가 1위**
(R@1 0.95 vs 0.89). 각자 자기 셋에서 이겼다 — **과적합이 양쪽에 있었다.**

그리고 팀원 골든셋은 변별력이 거의 없었다 — 16조합 전부 R@3=R@10=0.95로 동일. `course`까지
필터를 걸어 후보가 16~121건으로 좁혀지고 정답이 단일이라, 어떤 방식으로도 풀린다.

**확정적으로 가른 것은 RRF 하나뿐이었다** — 양쪽에서 일관되게 나빴다.

## 3. 팀원 코드에서 바꾼 것

### ① `keyword_search.py` — kiwipiepy → 문자 2-gram

| 랭킹 | kiwi Top-1 | 2gram Top-1 |
|---|---|---|
| BM25 단독 | 6/10 | **7/10** |
| BM25 주력 | 6/10 | **8/10** |
| dense 주력 | 9/10 | 9/10 |

**dense가 주력이면 차이가 없고, BM25 비중이 커질수록 2-gram이 앞선다.** 형태소 분석기가
단어를 잘못 쪼개는 손실("저작권"→"저작", "한살이"→"한"+"살이")이 BM25가 순위를 주도할 때
드러난다. 2-gram은 어절 원형을 토큰에 남기면서 조사 문제도 해결한다.

`kiwipiepy` 의존성 제거. 둘 다 쓰레기 토큰을 만들지만(2-gram은 "인수분해"에서 "수분")
BM25의 IDF가 흔한 조각의 기여를 눌러준다.

### ② `hybrid_search.py` — RRF → 가중합 (BM25 주력)

```
score = bm25_정규화 + 0.5 * dense_코사인
```

RRF를 뺀 이유: **점수 크기를 버리고 순위만 쓴다.** 실제 출력에서 한쪽에만 걸린 레코드가
전부 같은 점수(1/64)를 받아 서로 구분되지 않았다. 통과 28/38 vs 가중합 32/38.
`--fusion rrf`로 비교는 가능하게 남겼다.

BM25를 주력(기준선)으로 둔 이유: 슬롯 필터로 후보가 16~121건까지 좁혀진 뒤라 어휘 겹침만으로
대부분 풀린다. dense 주력이 Top-1 한 건을 더 맞히지만 노이즈가 1→3으로 늘었다.

### ③ `hybrid_search.py` — BM25 0건 게이트 추가

**이게 오늘 가장 쓸모 있는 발견이다.** 코사인 유사도에는 전역 임계값을 둘 수 없다:

| 질의 | 정답 | 1위 코사인 |
|---|---|---|
| 중학교 국어 "판소리 창법" | **0건** | **0.569** |
| 중학교 사회 "개발과 환경 보전 토론" | 있음 | 0.526 |
| "인수분해" | 있음 | 0.497 |

정답 없는 질의가 더 높다. 그런데 **BM25의 `score > 0`이 실제 임계값으로 작동한다** —
질의 단어가 후보 어디에도 없으면 0점이다. 0건이 정답인 케이스 3건 모두 정확히 0건을 반환했다.

| | 노이즈 | 통과 |
|---|---|---|
| 게이트 없음 | 33 | 29/38 |
| 게이트 적용 | **1** | **33/38** |

### 안 바꾼 것

- **임베딩 입력 `content + area`** — 프리픽스+explanation을 넣어봤지만 이 구성에서는
  Top-1이 8/10 → 7/10로 떨어졌다(R@10은 0.02 오름). 팀원 기본값이 맞다
- **슬롯 필터 `==` 정확 일치** — 내 `in`은 "과학"이 "과학 계열 선택 과목"까지 통과시킨다
- **후보군 기준 BM25 IDF** — 질의마다 BM25를 새로 만드는 방식. 후보가 수십~수백 건이라
  비용이 없고, 전체 기준 IDF보다 정확하다
- **`context_bundle.py`** — 성취기준을 찾은 뒤 그 course의 성격·목표·내용체계·교수학습을
  묶어 오는 코드. 내 쪽에 없던 조각이라 그대로 가져왔다

## 4. 골든셋 병합 — 42건 (평가 대상 38건)

`tr-*` 19건(팀원) + `nr-*` 22건(내 것) + `example` 1건.

**발견한 버그 두 개 (내 쪽 잘못):**

- **ID 충돌** — 양쪽 모두 `topic-01`~`topic-05`를 썼다. 첫 병합이 팀원 케이스 5건을
  덮어썼다. 출처 접두사(`tr-` / `nr-`)로 분리
- **`topic` 필드 오염** — 내 케이스의 주제에 슬롯 단어와 상투어가 남아 있었다:
  `"중학교 사회에서 개발과 환경 보전을 주제로 토론하는 수업의 성취기준"` →
  `"개발과 환경 보전을 둘러싼 토론"`. 실제 파이프라인에서 LLM이 `topic` 인자에 주제만
  넘길 테니 이게 현실과도 맞다. **이것만으로 점수가 5건쯤 올랐다.** 원문은
  `original_query`에 보존

**정답 수정 2건** (데이터를 다시 읽고 내 판단이 과했음을 확인):

- `nr-topic-01`: `9사(지리)06-02`(태평양 환경 문제) 제거 — 환경 문제이긴 하나
  개발 vs 보전 토론이 아니다
- `nr-special-04`: `6시자05-01`(단말기 구조·기능 탐색) 제거 — 문서 작성과 다르다

**`deferred` 3건** — `nr-doctype-01~03`은 서술 문서(purpose_goals/content_system/
teaching_assessment)를 정답으로 하는데 지금은 성취기준만 인덱싱하므로 채점에서 제외.
지우지 않고 남겨서 나중에 그 인덱스를 만들면 플래그만 떼면 된다.

**지표는 양쪽을 합쳤다** — MRR(팀원) + Top-1·메타·노이즈(내 것). MRR은 1위가 틀렸을 때도
2위인지 8위인지 구분해서 Top-1보다 정보가 많고, Top-1은 "1위가 맞나"를 바로 본다.

### must_not을 더 채우지 않기로 한 근거

노이즈 기준을 넣고/빼고 같은 튜닝 스윕을 돌려봤다:

| 스윕 | must_not이 결정을 바꿨나 |
|---|---|
| BM25 비중 (0.10~0.70) | **아니다.** 최적 구간이 같다 |
| 비성취기준 가중치 (1.0~0.7) | **그렇다.** 없으면 0.80이 0.90과 동점이 되는데, 0.80은 노이즈가 2→4로 두 배다 |

실제로 값을 하는 건 3~4건이다. 전부 채우는 건 과하고, "같은 영역 안에서 세부가 다른"
케이스(분수 덧셈 vs 곱셈, 인공지능 개념 vs 윤리)에만 쓰는 게 맞다. 팀원 19건에 소급해서
채우지 않았다.

### 최종 결정 — 공식 골든셋은 팀원 19건

병합한 42건 대신 **팀원이 `main`에 올린 19건(`4cc15f9`, 2026-10-08)을 공식 골든셋으로
유지하기로 했다.** 골든셋은 팀원이 관리한다.

다만 **그 19건으로는 검색 방식을 고를 수 없다** — `course`까지 좁혀 후보가 16~121건이고
정답이 단일이라 bm25 단독·가중합·RRF가 전부 19/19 만점으로 같다. 그래서 선정 근거가 된
내 22건은 `method-comparison-cases.jsonl`로 분리해 남겼고, `eval.py --golden method`로
언제든 재현할 수 있다. 그쪽에서는 hybrid 14/19 > bm25 12/19 > RRF 13/19로 차이가 드러난다.

## 5. 검토했지만 택하지 않은 것 — BM25 단독

BM25만으로 31/38이 나와서(게이트 덕에 0건 케이스 3건을 공짜로 통과) 임베딩을 빼는 안을
검토했다. 택하지 않은 이유:

- **전략 문서가 임베딩을 요구한다.** `NCIC_RAG_개발분업_전략`의 02절(A: Indexing
  Pipeline = Chunking→Embedding→Vector DB), 08절(Vector vs Hybrid 비교), 13절(최종 개발
  스토리)이 전부 임베딩 기반이다. 빼면 **팀원 A의 역할 전체가 산출물에서 사라진다**
- **Top-1 8/10 → 7/10, R@3 0.92 → 0.91** 손실. 1위가 틀리면 엉뚱한 성취기준을 근거로
  계획안이 나온다
- **어휘 불일치가 구조적이다.** 교사 말을 LLM이 `topic`으로 옮기는 구조라 "환경 보전" vs
  원문 "환경 보존" 같은 차이가 상시 생긴다. `nr-topic-01`에서 BM25 단독은 R@3 0.50,
  하이브리드는 1.00

지금 구성이 "BM25 주력 + dense 보조"라 사실상 키워드 중심이고, 전략 문서의 Hybrid 요구도
충족한다.
