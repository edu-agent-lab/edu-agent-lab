# 수업자료 생성 — 프롬프트에 무엇이 들어가나

> `apps/topic-retrieval/generate.py` 기준. 측정은 중학교 사회 "개발과 환경 보전을 둘러싼
> 토론" · 성취기준 1건 선택 · 토론 자료 기준.

## 검색과 생성이 보는 문서가 다르다

NCIC 원문은 과목마다 네 덩어리다.

```
1. 성격 및 목표            -> purpose_goals
2. 내용 체계 및 성취기준
   ├ 내용 체계 (표)        -> content_system
   └ 성취기준              -> achievement_standard
3. 교수·학습 및 평가        -> teaching_assessment
```

| | 검색(인덱스) | 생성(프롬프트) |
|---|---|---|
| `achievement_standard` | **O** (5,789건) | O |
| `purpose_goals` | X | **O** |
| `content_system` | X | **O** |
| `teaching_assessment` | X | **O** |

**검색은 성취기준만 한다.** 서술 문서 3종은 인덱스가 없어서 "평가 방법 알려줘" 같은
질의는 검색되지 않는다 (골든셋의 `doctype-*` 케이스가 `deferred`인 이유).

**생성에는 3종이 다 들어간다.** 검색이 아니라 `context_bundle.get_course_context()`가
course로 **조회**하기 때문이다 — 과목당 하나뿐이라 찾을 대상이 아니다.

## 프롬프트 구성비 — 맥락이 84%

| 블록 | 원본 | 프롬프트 | 비중 |
|---|---|---|---|
| 근거 성취기준 1건 (code·content·영역·학년군·해설·고려사항) | — | 1,000자 | 10% |
| 성격 (1번) | 964 | 964 | 10% |
| 목표 (1번) | 1,189 | 1,189 | 12% |
| 내용 체계 (2번) | **10,759** | **2,500** | 26% |
| 교수·학습의 방향 (3번) | 1,047 | 1,047 | 11% |
| 교수·학습 방법 (3번) | 973 | 973 | 10% |
| 평가의 방향 (3번) | 716 | 716 | 7% |
| 평가 방법 (3번) | 671 | 671 | 7% |
| **합계** | | **9,568자** (≈6,400토큰) | |

맥락 8,060자 = 84%. 성취기준 1건은 10%뿐이다.

`MAX_CONTEXT_CHARS = 2500`에 걸려 **내용 체계는 10,759자 중 2,500자만 들어간다** —
중간이 끊긴 채로 간다.

### 내용 체계는 관련 영역만 넣도록 바꿨다

위 표는 바꾸기 전 측정이다. 내용 체계 표는 영역 순서("(1) 지리 인식" ... "(11) 한국사")로
나열돼 있어서 앞 2,500자는 (1)~(3) 영역일 뿐이었다. 이 측정 예시의 성취기준
`9사(지리)12-02`가 속한 "(4) 지속가능한 세계"는 3,453자에서 시작해 **통째로 빠져 있었다.**

지금은 2,500자를 넘는 내용 체계 표는 선택한 성취기준이 속한 영역만 넣는다
(`content_areas.py`). 위 예시는 2,500자(엉뚱한 영역) -> 999자("(4) 지속가능한 세계"만).

- 영역 찾기: 성취기준 area와 표 제목이 같으면 그 영역, 아니면 성취기준 문장+area와 각 영역
  블록을 BM25로 비교. 성취기준 코드로는 못 찾는다 — 성취기준 area는 단원 단위
  ("9사(지리)12 지속가능한 세계와 글로컬 시민"), 표는 초3~중3을 아우르는 큰 영역
  ("(4) 지속가능한 세계")이라 번호가 이어지지 않는다
- 정확도: 이름이 같은 1,496건을 정답으로 놓고 내용 비교만 돌리면 1,454건(97%). 실제로는
  이름이 같으면 이름으로 고르므로 이 1,496건은 100%이고, 내용 비교는 나머지 259건에 쓴다
- 2,500자를 넘는 일반 교과 내용 체계 36건은 모두 영역 제목이 있다. 짧은 표는 그대로 넣는다
- 성취기준이 여러 영역에 걸치면 해당 영역을 모두 넣고, 고른 영역은 자르지 않는다

## 알려진 문제 두 개 (②는 고침)

### ① 비용 대비 쓸모가 어긋나 있다

계획서 작성에 실제로 쓰이는 정도로 보면:

| 문서 | 내용 | 계획서에 쓰임 | 프롬프트 비중 |
|---|---|---|---|
| 성격·목표 | "과학은 ~하는 교과이다" 같은 과목 전체 철학 | **거의 없음** — 어느 차시든 같은 문장 | 22% |
| 내용 체계 | 전 학년·전 영역의 핵심 개념 표 | **낮음** — "이 단원이 어디쯤인지" 정도 | 26% |
| 교수·학습/평가 | 과목 전체의 교수·평가 방법 일반론 | **중간** — 평가 계획 칸 쓸 때 참고할 만함 | 35% |

**가장 쓸모 적은 1·2번이 48%를 먹는다.** 빼면 프롬프트가 9,568 -> 약 4,400자로 절반이
되고, 비용·지연시간이 줄며 LLM이 핵심에 집중한다.

고치는 방향 세 가지:

1. **1·2번 제외** — 교수·학습 및 평가만 넣는다. 가장 간단하다
2. **자료 유형별로 다르게** — 퀴즈·활동지는 평가 방법 위주, 수업계획안은 내용 체계의
   핵심 아이디어도. 유형이 이미 프롬프트 변수라 붙이기 쉽다
3. **화면에서 선택** — 어떤 맥락을 넣을지 체크박스로

지금은 **전부 넣는 쪽**으로 두고 있다. 생성 품질을 평가할 기준이 아직 없어서(정답이 없는
산출물이라 골든셋 불가) "뺐더니 나빠졌는지"를 잴 수 없기 때문이다. 품질 체크리스트를
만든 뒤에 비교하는 게 순서다.

### ② 성취기준 코드 인용이 과하다

프롬프트의 "각 활동이 어느 성취기준에 해당하는지 코드를 괄호로 밝힌다"가 문장마다
적용된다. 성취기준이 1건일 때 특히 지저분하다 — 실제 생성 결과에서 거의 모든 줄 끝에
`(9사(지리)12-02)`가 붙었다.

고치는 방향:

1. 조건부 — "성취기준이 2건 이상일 때만 코드를 표시한다"
2. 위치 한정 — "차시·활동 제목 뒤에만 표시하고 본문 문장마다 붙이지 않는다"

2번이 나아 보인다. 1건이어도 어느 활동이 근거에 해당하는지는 표시할 값이 있다.

**고침:** 코드는 '자료 개요'와 '수업 목표'에서만 밝히게 했다. 같은 예시에서 70회 넘게
붙던 코드가 3~4회로 줄었다.

## 출력 틀 — 모든 자료 유형이 같은 8개 항목

항목을 정하지 않았을 때는 모델이 준비물·교사 유의사항·차시별 형성평가·차별화·현장 연계·
맺음말을 알아서 붙여 장황해지고, 정작 필요한 배경 읽기 자료·핵심 개념·활동지 예시는
빠졌다. 지금은 `generate.SECTIONS` 8개 항목만, 이 순서대로 쓰게 한다.

```
자료 개요 · 수업 목표 · 배경 읽기 자료 · 핵심 개념 · 토론 쟁점 · 수업 흐름 · 학생 활동지 예시 · 평가 루브릭
```

- 자료 유형(수업계획안/활동지/퀴즈/토론 자료)은 틀을 바꾸지 않고 어느 항목을 자세히 쓸지만
  정한다. 퀴즈는 '학생 활동지 예시'에 문항을, '평가 루브릭' 끝에 정답표를 둔다
- **배경 읽기 자료는 근거 성취기준(해설·고려사항)과 과목 맥락 안의 내용만으로 쓴 개념 설명
  글로 한정한다.** 그 밖의 사례·통계·연도·지명·인물은 넣지 않는다
- 지시문 문장을 본문에 옮겨 쓰거나("차시별로 ~ 자세히 제시한다") 작성 중 고민을 남기는
  경우("정답은 D? 주의:")가 있어서 둘 다 금지했다
- 4개 유형 생성 결과(중학교 사회 `9사(지리)12-02`): 8개 항목 누락·추가 0, 근거 외 코드 0,
  3,582~4,714자. 예시는 `samples/`

## 할루시네이션 방어 — 세 겹

| 장치 | 위치 |
|---|---|
| 성취기준을 LLM이 고르지 않는다 | **코드** — 사용자가 화면에서 체크한 것만 넘긴다 |
| "제시된 성취기준만 근거로, 코드를 지어내지 않는다" | system + 요구사항 |
| "없는 사실(통계·수치)은 쓰지 않는다. 필요하면 '교사가 지역 사례로 교체' 안내로" | 요구사항 |

프로젝트 1에서 배운 패턴이다 — "~하지 마세요"만으로는 안 지켜지고 **코드로 막는 게
확실하다** (`summarizer.py`가 빈 본문일 때 LLM 호출 자체를 막은 것처럼). 그래서 성취기준
선택을 코드로 고정했다.

실제 생성 1회 확인(토론 자료, 41초, 3,219자): 본문에 등장한 성취기준 코드가 근거로 준
1건과 정확히 일치했고 지어낸 코드는 없었다. 구체적 수치 대신 "교사가 지역 사례로 교체"
안내를 남겼다.

## 해설 앞 성취기준 코드 복원

크롤러가 해설 앞의 코드를 떼어내면서 조사만 남은 경우가 **약 938건** 있다.

```
원문:  [9사(지리)12-02]는 다양한 스케일에서 일어나는 ~
데이터: 는 다양한 스케일에서 일어나는 ~
```

그대로 프롬프트에 넣으면 문장이 깨지므로 `generate.restore_explanation()`이 코드를
되돌려 붙인다.

**주의: `이 성취기준은 ~`으로 시작하는 1,398건은 정상 문장이다.** 둘 다 첫 토큰이 한 글자
조사 모양이라 형태만으로는 못 가른다. 그래서 깨진 쪽의 조사 목록(`은 `, `는 `, `에서는 `,
`의 `, `성취기준은 ` 등)을 명시해 그것만 복원한다.

## 평가 — 아직 없다

생성 품질은 **골든셋으로 못 잰다.** 좋은 수업계획안이 하나로 정해지지 않기 때문이다.
체크리스트가 필요하다:

- 요청한 학교급·과목과 일치하는가
- 근거로 준 성취기준만 인용했는가 (자동 검사 가능 — 정규식으로 코드 추출해 대조)
- 자료 유형이 요구한 형식을 갖췄는가 (계획안이면 차시·시간 배분, 퀴즈면 정답·채점 기준)
- 없는 사실(통계·수치)을 지어내지 않았는가

두 번째는 자동화할 수 있고, 나머지는 사람이 본다.
