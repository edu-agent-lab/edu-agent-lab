# 파이프라인 & 화면 설계 (Day3)

질의 → MCP tool call → 요약 → 결과 표시로 이어지는 전체 흐름.

> 가이드 Day3 초안과 다른 부분이 몇 군데 있다. Day1 실측(연동 방식)과 Day2 골든셋 구성
> 과정에서 데이터를 직접 열어보고 조정한 결과이고, 각 항목에 이유를 적어뒀다.
>
> **Step 5(기술 스택 확정)는 팀 논의 전이라 비워뒀다.**

## Step 1. 전체 파이프라인

```text
사용자 자연어 질의 입력
     ↓
① 질의 유형 판단 + 검색 조건 구성        query_classifier.py
     ↓                                  → QueryIntent
② 데이터셋 전체 조회 (앱 시작 시 1회)     mcp_client.py
     ↓                                  → list[NotionPage]
③ 필터링 · 매칭 · 랭킹                   search.py
     ↓                                  → list[PageMeta]
④ 검색 결과 요약 문단 생성                search.describe_results()
     ↓                                  → str
⑤ 페이지별 요약 생성 (LLM)               summarizer.py
     ↓                                  → str
⑥ 검색창 + 요약 + 결과 리스트 표시        app.py
```

### 가이드 초안과 다른 점

**가이드 ①②를 하나로 합쳤다.** "유형 판단"과 "검색 질의 구성"을 나눌 실익이 없었다.
`classify_query()`가 `QueryIntent` 하나를 돌려주고 끝난다.

**가이드 ③④(`notion-search` → `notion-fetch`)를 전체 조회 1회로 바꿨다.** 이유 세 가지:

- `API-post-search`는 **제목만** 검색한다. "토론"으로 찾으면 제목에 그 단어가 없는
  `근대화 과정에서 외세의 수용은 불가피했는가?`가 빠진다.
- 데이터가 **14건뿐**이라 전부 메모리에 올려도 부담이 없다.
- 속성이 절반쯤 비어 있어(과목 7/14, 학년 6/14 누락) **속성 → 본문 → 제목** 순으로
  폴백해야 하는데, 그러려면 데이터가 손에 있어야 한다.

데이터가 크게 늘면 서버 사이드 필터링으로 되돌려야 한다.

**③(필터링·랭킹) 단계를 새로 넣었다.** 위 폴백과 정규화가 들어갈 자리가 필요했다.
`mcp_client`는 가져오기만 하고, 검색 품질에 관한 로직은 전부 여기 모은다.
골든셋 점수를 올리려고 반복해서 고칠 코드를 한곳에 두기 위해서다.

**④(검색 결과 요약)를 명시했다.** 프로젝트 스펙의 웹 인터페이스 필수 요소
"검색 결과 요약 텍스트"에 해당한다.

## Step 2. 각 단계의 입/출력 데이터 형식

Streamlit 단일 프로세스라 단계 사이에 직렬화 경계가 없다. JSON 대신 **데이터클래스**를
그대로 주고받는다. 가이드의 ⑤(화면 표시용 JSON)에 해당하는 형태를 따로 두지 않은 이유다.

### ① 질의 유형 판단 결과 — `QueryIntent`

```python
QueryIntent(
    query_type = QueryType.TOPIC,      # topic | title | attribute
    keyword    = "부등식",              # 주제어. 없으면 None
    filters    = QueryFilters(
        grade     = None,              # "고1"
        subject   = "수학",             # 국어/영어/수학/사회/과학/한국사/정보
        date_from = None,              # ISO 8601 (YYYY-MM-DD)
        date_to   = None,
    ),
    degraded   = False,                # LLM을 못 불러 규칙만으로 만든 결과인지
)
```

`degraded`는 나중에 추가한 필드다. 기본값이 있어서 기존 호출부는 그대로 둬도 되고,
화면에서 "이 결과는 AI 분석 없이 나왔다"를 알릴 때만 본다. 근거는 Step 6 참고.

**`filters`는 유형과 무관하게 항상 채운다.** 실제 질의는 "고1 토론 자료"처럼 섞여
들어와서 유형 하나로 표현되지 않는다. `query_type`은 "텍스트를 제목으로 볼지
키워드로 볼지"만 정한다.

**가이드의 `date_range`(문자열)를 `date_from`/`date_to`(ISO)로 바꿨다.** "지난달"을
나중에 파싱하려면 결국 오늘 날짜가 필요한데, 그 계산을 두 군데로 나눌 이유가 없다.
분류 프롬프트에 오늘 날짜를 주입해 ISO 범위를 바로 받는다.

### ② MCP 조회 결과 — `NotionPage`

```python
NotionPage(
    page_id    = "ca39feee-0a11-827b-bcf5-81ea9f4377dc",
    title      = "통합 국어 1 토론 구성하기",
    url        = "https://app.notion.com/p/1-ca39feee...",
    content    = "## 기본 정보\n- 대상: 고등학교 1학년 1학기\n- 과목: 공통국어1\n...",
    properties = {"학년": {...}, "다중 선택": {...}, "날짜": {...}, "학기": {...}},
)
```

**`properties`는 Notion 원본 그대로 담는다.** 가공해서 담으면 나중에 필요한 필드가
생길 때마다 이 파일을 고쳐야 한다. 접근은 `mcp_client`의 헬퍼
(`title_of` / `grade_of` / `subjects_of` / `date_of` / `semester_of`)로 한다.
타입마다 빈 값 모양이 달라서(`select`는 `None`, `multi_select`는 `[]`) 방어가 필요하다.

### ③ 검색 결과 — `PageMeta`

속성·본문·제목을 합쳐 검색에 바로 쓸 수 있게 만든 형태.

```python
PageMeta(
    page          = NotionPage(...),
    title         = "다항식의 연산과 인수분해 퀴즈",
    subject_keys  = ["수학"],        # 속성 → 본문 → 제목 순 폴백, 대표 키로 정규화
    grade         = "고1",
    date          = "2025-07-07",
    semester      = "25-2",
    material_type = "퀴즈",          # 본문 `- 자료 유형:` 또는 제목에서 추론
    is_request    = True,            # 본문에 `원하는 활동 자료 유형` 필드가 있으면 요청서
    body_fields   = {"대상": "고등학교 1학년 1학기", "과목": "공통수학1", ...},
)
```

`subject_keys`가 `["공통수학1"]`이 아니라 `["수학"]`인 이유: 속성은 `공통 영어1`(공백 있음),
본문은 `공통영어1`(공백 없음)로 표기가 달라서 그대로는 비교가 안 된다. 공백과 숫자를
지운 뒤 대표 키로 정규화한다.

### ④ 검색 결과 요약 — `str`

```
"수학 자료 3건을 찾았습니다. 프로젝트 2건, 퀴즈 1건입니다. 이 중 2건은 자료 생성 요청서입니다."
```

LLM을 부르지 않는다. 필요한 정보(자료 유형, 과목, 날짜, 요청서 여부)가 `PageMeta`에
이미 다 있고, 이 영역은 화면 맨 위라 결과가 나오자마자 보여야 한다. 페이지별 요약을
기다렸다가 만들면 맨 위 문장이 가장 늦게 뜬다. 규칙 기반이라 골든셋으로 검증도 된다.

### ⑤ 페이지별 요약 — `str`

```
"고1 1학기 공통수학1 퀴즈. 다항식 연산과 인수분해 개념을 확인하며,
 오답 케이스를 분류해 채점 자동화까지 염두에 두었다."
```

## Step 3. 요약 생성 프롬프트

`prompt.SUMMARIZE_PAGE_PROMPT` 참고. 가이드 초안을 따르되 두 가지를 바꿨다.

- **"자료 유형(퀴즈/프로젝트/토론/교안)"을 필수 항목에 넣었다.** 본문 앞머리
  `- 자료 유형:` 필드에서 얻을 수 있고, 검색 결과 목록에서 가장 먼저 알고 싶은 정보다.
- **좋은 예/나쁜 예를 넣었다.** "~하지 마세요"만 적었더니 "이 자료는"이 계속
  새어나왔다. 원하는 형태를 보여주니 사라졌다.

분류용 프롬프트(`CLASSIFY_QUERY_PROMPT`)는 Day2 Step2 산출물이고 같은 파일에 있다.

```text

├──────────────────────────────────────────────────────┤

│  이 중 2건은 자료 생성 요청서입니다.                     │
├──────────────────────────────────────────────────────┤
│  ┌────────────────────────────────────────────────┐  │
│  │ 생활 속 비용 조건을 부등식으로 비교하기            │  │
│  │ 프로젝트 · 수학 · 고1 · 2025-09-18               │  │

│  └────────────────────────────────────────────────┘  │

└──────────────────────────────────────────────────────┘
```

`app.py`에 구현되어 있다. 카드 메타 줄은 가이드의 "제목 · 카테고리 · 날짜"를
데이터셋에 맞춰 **자료유형 · 과목 · 학년 · 날짜 · (요청서)** 로 바꿨다.
`카테고리`라는 속성이 데이터셋에 없고, 학년은 값이 `고1` 하나뿐이라 자료 유형이
실질적인 구분 축이기 때문이다.

결과가 많으면 상위 8건만 보여준다. 카드마다 LLM을 한 번씩 부르므로 전부 요약하면
그만큼 느려진다.

선택 기능(정렬, 필터 UI, 복수 페이지 비교)은 이 최소 구조가 안정적으로 돌아간 뒤에.

## Step 6. 운영 제약

### 알려진 한도

- `API-post-search` 분당 30회 / 그 외 분당 180회(= 초당 3회)
- `fetch_all_pages()`가 목록 1회 + 본문 14회 = **15회를 순차 호출**한다

15회가 한도 아래이긴 하지만 여유가 크지 않다. 왕복이 빠르면 초당 3회에 붙는다.

### 호출 간격

**고정 sleep을 넣지 않고, 직전 호출로부터 흐른 시간을 재서 모자란 만큼만 쉰다**
(`mcp_client.MIN_CALL_INTERVAL = 1/3`).

가이드 초안은 매 호출 뒤 `asyncio.sleep(0.35)`를 넣는 방식인데, 그러면 14건에서 항상
5초를 더 낸다. 실제로는 네트워크 왕복만으로 이미 간격이 벌어지는 경우가 많아서, 그때는
추가 대기가 0이 되는 편이 낫다. 한도에 붙는 상황에서만 비용을 낸다.

### 재시도

| 항목 | 값 |
|---|---|
| 최대 재시도 | 3회 (총 4회 시도) |
| 대기 | 응답의 `Retry-After` 우선, 없으면 0.5 → 1 → 2초 |
| `Retry-After` 상한 | 10초. 넘으면 기다리지 않고 실패로 끝낸다 |
| 재시도 대상 | 429 / rate limit / 502·503·504 / timeout / 연결 끊김 |
| 재시도 안 함 | 401, 404 등. 다시 걸어도 결과가 같다 |

상한을 두는 이유: Streamlit 첫 화면이 `fetch_all_pages()`를 기다리므로, 오래 매달리는
것보다 실패로 끝내고 사용자에게 알리는 편이 낫다.

실패하면 `MCPCallError`를 올리고 `app.py`가 안내 메시지로 바꾼다.

### LLM 실패

분류 단계에서 LLM을 못 부르면(인증 오류, 429, JSON 형식 위반) **규칙 기반 결과로
물러선다** — 상투어만 걷어낸 나머지를 키워드로 보는 TOPIC 질의. `QueryIntent.degraded`가
켜지고 화면에 "단순 키워드 검색으로 대체했습니다" 경고가 뜬다.

날짜 조건("지난달")은 이 경로에서 해석되지 않으므로 결과가 비거나 엉뚱해질 수 있다.
검색이 틀리는 것보다 화면이 죽는 게 나쁘다고 보고 택한 절충이다.

요약 단계는 폴백하지 않는다. 카드별 `try/except`로 그 카드만 "요약을 만들지
못했습니다"로 남고 검색 결과 자체는 유지된다.

### 남은 것

- 데이터가 늘어 전체 조회가 부담이 되면 호출 간격 조절만으로는 부족하다.
  서버 사이드 필터링으로 되돌려야 한다 (Step 1 참고).
